## Context

动机与范围见 `proposal.md`，行为契约见 `specs/`。完整的现状分析、线上核实数据、逐字段实现细节与代码位置索引在 `docs/admin-ui-credential-list-display-and-query-optimization-design.md`，本文只记录支撑那份文档的技术决策与风险。

约束方面有几点决定了可选空间：

`MultiTokenManager` 的对外读取全部走 `snapshot()` 返回的 `ManagerSnapshot`，Admin service 拿不到内部结构。所以「让列表带上订阅等级」必须从 `CredentialEntrySnapshot` 起手，不能在 handler 层临时拼。

余额缓存是 `parking_lot::Mutex<HashMap<u64, CachedBalance>>`，TTL 300 秒，另有 `kiro_balance_cache.json` 持久化。缓存已经有数据，线上 10 条凭据的缓存全部在 TTL 内，这是 P4 能纯读实现的前提。

Admin UI 经 rust-embed 嵌入二进制，与后端同版本发布。前后端不存在版本错配窗口，这是敢做破坏性响应形态变更的依据。

`admin-ui/package.json` 无 `react-router`。URL 状态同步不能依赖路由库。

## Goals / Non-Goals

**Goals:**

- 列表接口一次请求就能满足首屏所需，包括订阅等级与用量，且仍是纯内存同步读取
- 筛选与分页只在服务端实现一次，前端不留本地过滤兜底路径
- 分页在优先级重复的情况下不重不漏
- 分页 UI 在页数很多时可用，且键盘与读屏可完整操作

**Non-Goals:**

- 不做游标分页。凭据集合规模在几十到几百条，`page`/`perPage` 的偏移分页足够，且能提供 `totalPages` 与直接跳页，游标分页反而丢掉这两项
- 不做启动时余额缓存预热
- 不改余额缓存的 TTL、持久化格式与批量刷新逻辑
- 不引入路由库
- 不做筛选条件的服务端持久化（保存的视图 / 预设）

## Decisions

### 分页放在服务端，且不保留「不传参数返回全量」的兼容路径

考虑过的折中是：`page` 缺省时返回全量数组，传了才分页。否决它的理由有三条。接口会有两种互斥响应形态，调用方必须先判断字段存在性才知道拿到的是什么；`pageInfo` 从必有变成可选，前端类型里多出一层 `undefined` 分支；最关键的是默认的 30 秒轮询不带参数，仍然全量传输，恰好绕开了这次要解决的问题。

既然前后端同版本发布，一次把形态改干净比留一个长期歧义划算。外部脚本消费者的迁移成本是显式传 `perPage`，或读 `pageInfo.totalPages` 逐页取回。

### 借鉴 GitHub REST API 的分页契约，但不含 Link 头

采用它的两条具体做法：`per_page` 有硬上限；越界页返回空数组而非 4xx。

越界返回 200 空数组这点值得单独说。分页参数来自 UI 状态或收藏的链接，凭据集合会随删除、禁用、筛选而缩小，「页码超出范围」是正常的时序结果而非客户端错误。返回 4xx 会让前端不得不把预期内的情况当异常处理。

`Link` 头不采用。最初的设计里它占了一整条 Requirement 加三个 scenario，但评审时发现没有消费者：本仓库唯一的调用方是同版本发布的内嵌 Admin UI，它的分页控件按 `pageInfo` 的 `hasPrev` / `hasNext` / `totalPages` 推页码，前端契约里一次都没提到 `Link`。为一个假想的外部脚本消费者维护第二套导航事实源，代价是 handler 返回类型变成 `(HeaderMap, Json<T>)`，收益是零，且两套一旦不一致就无从判断以哪个为准。

导航信息因此只由 `pageInfo` 提供。基数与导航同在响应体里，不再有「头承载导航、体承载基数」的分工，但换来的是单一事实源。

### `page` / `perPage` 用 `i64` 反序列化

spec 要求「`page` 小于 1 时 clamp 为 1」。这条在 `u32` 上几乎无意义：`page=-1` 会在 `Query` 提取阶段就被 serde 拒成 400，唯一能进 clamp 的「小于 1」只有 `0`。

用 `i64` 接，让负值走完 clamp 路径。代价是类型比业务语义宽，需要在 clamp 后转回无符号使用。

`page=abc` 这类无法解析为整数的输入仍然返回 400，这不违反「clamp 而非报错」。clamp 承诺覆盖的是「类型正确但取值越界」，不是「类型错误」。这个边界在 spec 里写明了，否则实现者会为了满足「MUST NOT 返回 4xx」去写一个吞掉所有解析错误的自定义 Deserializer。

### 处理顺序固定为 filter → sort → paginate

三步不可交换。先切页再筛选，每页条数变得不确定；先切页再排序，页边界会随内容漂移。这个顺序在 spec 里写成了规范条款，因为它是可观察行为的一部分，不只是实现细节。

### 排序键改为 `(priority, id)`

现有 `sort_by_key(|c| c.priority)` 不是全序：`priority` 允许重复，重复项的相对顺序由 `sort_by_key` 的稳定性加上原始 `Vec` 顺序决定，而原始顺序会因增删凭据变化。假分页把这个缺陷掩盖了：前端拿到全量再切片，即使顺序不稳也是「同一份数据的一致切片」。服务端分页后，两次请求之间顺序若有变化，同一条凭据会跨页重复或整条漏掉。

`id` 是 `u64` 且唯一，`(priority, id)` 构成全序，代价是一次元组比较。

这项修正必须和分页同一批发布，单独发布会改变现有列表的展示顺序而没有任何收益。

### 列表内联余额快照，而不是列表内触发查询

P4 的诱惑是在列表构造时对缺失余额的凭据补一次查询。不做，理由是列表是 30 秒轮询的高频路径，一次请求会放大成 N 个上游调用，并且和 `admin-ui-balance-ops` 「不发出未经操作者授权的自动请求」的取向冲突。

改为只读缓存快照，并强制携带 `cachedAt` / `ageSecs` / `stale`。披露新鲜度是这个决策的成立条件：不标注就等于把 5 分钟前的数值伪装成实时值，那比显示「未查询」更糟。

`cachedAt` 用 Unix 秒，不用 RFC3339。理由是就近一致：`CachedBalance.cached_at` 本身是 `f64` Unix 秒，同一个快照结构体里的 `nextResetAt` 也是 Unix 秒（沿用 `BalanceResponse` 的既有形态），前端类型里对应 `number`。让 `cachedAt` 单独用字符串，等于在同一个对象里放两种时间表示，还要在服务端多做一次格式化。

快照生成时一次性 `self.balance_cache.lock().clone()` 拿到整张表，而不是逐条凭据加锁。凭据几十条，克隆一张小 HashMap 的代价低于几十次锁竞争。

### 订阅等级有两个服务端来源，以落盘值为准

`subscriptionTitle` 在响应里会出现两次：列表项顶层（来自凭据落盘值），以及余额快照内部（`BalanceResponse` 自带该字段）。两者可能不一致。

落盘值在额度查询成功且取值发生变化时回写并持久化；快照内的值是余额缓存写入时刻的附带值。缓存可能比落盘值旧，所以顶层优先。

前端的取值链因此是三级：本次会话的实时查询 → 顶层 `subscriptionTitle` → 快照内的值。这个顺序要写进 spec，否则实现者面对两个同名字段只能靠猜。

### facets 独立端点，而不是塞进列表响应

服务端分页后，筛选下拉框的可选值不能再从当前页数据去重生成。当前页可能一个 `social` 凭据都没有，但系统里有。

两个方案：列表响应附带 facets，或独立端点。选独立端点，因为 facets 只在页面初始化时需要，附在 30 秒轮询的列表响应里是每轮都传一遍不变的数据。

### `__unknown__` 哨兵值表示「无订阅等级」

「按订阅等级筛选」需要能筛出「没有订阅等级」这一类。可选做法是加一个 `subscriptionTitleIsNull` 布尔参数，或用哨兵值。选哨兵值，因为它让下拉框的选项与查询参数一一对应，前端不需要为「未知」这个选项走另一条参数路径。

风险是真实订阅等级恰好叫 `__unknown__`。双下划线包裹的形式在 AWS 订阅名称里不会出现，接受这个风险。

### URL 状态同步用 `history.replaceState`

没有路由库，直接操作 History API。用 `replaceState` 而非 `pushState`：筛选条件在防抖后仍可能连续变化，`pushState` 会往历史栈里塞一堆中间状态，浏览器返回键变得不可用。代价是无法用返回键撤销筛选，这个取舍对运维面板可以接受。

### 页码折叠采用 Primer 的双参数模型

`marginPageCount`（首尾各保留几页）与 `surroundingPageCount`（当前页两侧各保留几页）两个参数，比「最多显示 N 个页码」的单参数模型更好控制：后者在当前页靠近边界时会出现页码条宽度跳变。

折叠算法抽成 `admin-ui/src/lib/pagination.ts` 里的纯函数 `buildPageItems`，不依赖 React。这样页码序列可以直接单测，不必渲染组件。

一个容易漏的细节：当折叠区间只剩一页时，渲染省略号是错的。省略号占的宽度和一个页码差不多，却少给了一个可点击目标。这种情况直接渲染那一页。

### 新增全选控件，作用域限定为当前页

现有实现没有全选控件，只有逐个勾选和「取消选择」。凭据条数上去之后，勾满一页要点十二次，这个缺口本来就该补。本次一并做掉。

作用域有两条路：让全选发请求取回筛选后全集的 id，或限定为当前页。选当前页。「对筛选后的 200 条凭据一次性批量验活」是高风险操作，让它需要显式逐页确认是合理的摩擦。

已选凭据跨页保留，翻页不清空，否则「翻页看一眼再回来」就会丢掉选择。由此控件需要三态：当前页全部已选、部分已选、未选。当前页已全选时再次点击只取消本页，不动其他页的已选项。同时 UI 要显示跨页已选计数，否则操作者会在翻页后误以为之前的选择丢了。

`admin-ui-balance-ops` 里「定时刷新作用于当前页」的既有条款在这个模型下自动成立，「当前页」的来源从前端切片结果变成服务端返回结果，语义不变。

### 选中状态从 id 集合升级为携带属性的快照

现有实现里 `selectedIds` 是 `Set<number>`，需要凭据属性时回列表响应里 `find(c => c.id === id)`。这个模式在假分页下成立，因为前端持有全量数据，反查必然命中。

服务端分页后它会失配，而且失配的方式很难察觉。跨页已选的 id 反查得到 `undefined`，取属性得到 `undefined`，在布尔判断里退化为「不满足条件」。批量删除因此认为这条凭据未被禁用，把它算进「已跳过」的计数。操作者看到「已选 5 条，跳过 3 条」，以为那 3 条不符合条件，实际只是没加载。

四处都有这个模式：已选禁用数统计、批量删除、批量恢复、批量刷新 Token。改法是让选中集合保存做判断所需的属性，在勾选那一刻从当前页数据里取。要存的不止 `disabled`，批量恢复判的是 `failureCount > 0`。

批量验活是第五处读取点，但它只用 id 不取属性，本身不受分页影响。它仍要跟改：`Set` 换成 `Map` 后 `Array.from(selectedIds)` 会得到 `[id, value]` 元组而不是 id 数组。这类跟改点靠类型检查兜住。

代价是选中状态里的属性可能过期，凭据在被选中后被他处改了状态。这个代价可控：后端操作本身会校验前置条件并返回错误，前端汇总里如实计为失败即可。这比「静默剔除并计入跳过」诚实得多，前者操作者能看到失败原因，后者看不出任何异常。

### 前端实时余额缓存按 id 存活，与当前页解耦

`balanceMap` 现有的清理逻辑是「保留出现在 `data.credentials` 里的 id」，目的是删除凭据后不留残影。分页前这个判据等价于「凭据仍存在」，分页后不再等价，翻页会让其他页的凭据暂时消失。

按原逻辑，翻页一次就把其他页已查到的实时余额全部丢掉。后果不只是白查一遍：卡片会从实时态退回缓存态，新鲜度标注重新出现，而 spec 明确要求「实时查询成功后新鲜度标注消失」。翻页往返一趟就能让这条要求被违反。

判据要改成「凭据已从系统中删除」。最省的实现是让清理只在明确得知删除后执行（删除操作成功回调），而不是每次列表响应都做一次全量对账。

### 声称全量的操作必须与实际范围对齐

「清除所有已禁用凭据」这个入口分页前依据前端全量数据判定范围，措辞与行为一致。分页后实现不变的话，它会静默变成「清除当前页的已禁用凭据」，而确认文案仍写「清除所有 N 个」，其中 N 也是当前页的计数。操作者以为清空了全部，实际只清了一页。

两条路都可行：改成显式的当前页语义（措辞同步改），或保留全量语义。前者简单，后者更贴合运维意图：「清空所有已禁用凭据」本来就是个全量动作，拆成逐页点确实很别扭。

选后者。这个入口本身就是为「一次清干净」存在的，收紧成当前页等于取消了它的价值。

要改两处，来源不同。按钮可用性与确认文案的条数用 `total - available`：这两个基数都不受筛选与分页影响，相减就是全量已禁用数，不必额外请求也不必后端加字段。现在用的 `disabledCredentialCount` 是当页统计，一个全量语义的入口不能用当页计数决定是否可用，当页恰好没有已禁用凭据时按钮会被禁掉，而系统里明明有。

删除范围不能这么省。它需要的是 id 列表而不是计数，得带 `disabled=true` 逐页取回。这一步只在操作者确认执行时做，不进首屏路径。原实现从 `data.credentials` 过滤，分页后那个数组只剩当前页，删除范围本身就退化了，不只是计数错。

### react-query 的 queryKey 与 placeholderData

查询对象整体进 `queryKey`，让每种筛选组合各自缓存。副作用是 key 碎片化，缓存条目变多，但每条只有一页数据，内存可控。

配 `placeholderData: (prev) => prev`，翻页时保留上一页内容并显示加载态。没有它，每次翻页列表会先闪回空白，在 30 秒轮询的场景下尤其难受。

## Risks / Trade-offs

- [外部脚本消费者拿到的凭据从全量变成前 12 条，且不报错] → 这是最容易埋雷的一项，因为它静默生效。版本说明与 README 显式标注 breaking，`README.md` 的接口清单同步改写描述；建议消费者显式传 `perPage` 并按 `pageInfo` 逐页取回。
- [分页后前端三处静默退化] → 实时余额被翻页丢弃、批量操作跨页反查失配、全量清除退化为当页。三者的共同点是不报错、不崩溃，只是行为悄悄变了，而其中两处会让操作者看到错误的计数。这是本次变更风险最高的一项，缓解见 Decisions 里对应的三条决策，验收项列在 tasks 第 6 组。
- [`admin-ui-model-ops` 的 `modelCount` 约束作用域收窄] → 该 capability 要求列表每项带 `modelCount`，分页后只对当前页成立。字段构成不变，约束本身不破；但依赖「遍历一次列表找出缺模型缓存的凭据」的用法会漏，需逐页取回。这一条在 proposal 的 Impact 里显式记录。
- [`(priority, id)` 全序化改变现有列表顺序] → 同优先级凭据的相对位置会变。与分页同批发布，顺序变化被更大的列表形态变更吸收；运维者不会把「同优先级内的顺序」当作稳定契约。
- [缓存披露语义做得不到位，操作者把缓存值当实时值] → 这是 P4 唯一的真实风险，也是评审最该盯的地方。`stale` 为 `true` 时视觉弱化并加过期提示；实时查询成功后新鲜度标注必须消失，否则两种状态在视觉上会混同。
- [`__unknown__` 与真实订阅等级冲突] → 概率极低，若发生则该等级的凭据无法被单独筛出。接受；若真出现，改为在 facets 响应中返回转义后的哨兵值。
- [筛选组合过多导致 react-query 缓存膨胀] → 每种组合一个缓存条目。单条只有一页数据；必要时收紧 `gcTime`。
- [endpoint 徽章收敛的实际收益很小] → `src/main.rs:120-123` 只注册 `ide` 一个端点，`src/model/config.rs:339` 默认值也是 `ide`，`src/admin/service.rs:134` 又把凭据缺省值兜底为默认端点。三者叠加的结果是所有凭据的 endpoint 恒等于默认，徽章恒省略，「不等时渲染」永不触发。接受现状：这条收敛的价值就是去掉一枚永远冗余的徽章，判断逻辑留着是为多端点场景，不为不可达分支写验收断言。

此前记录的「默认 endpoint 取值未确认」已作废。不需要读线上 `config.json`，仓库内三处证据已经能确定取值，`README.md:190` 也写明「仅已注册名，当前 `ide`」。

## Migration Plan

分三阶段，前两阶段可独立发布。

**阶段一（P4，非 breaking）**：快照导出 `subscription_title` → 列表契约暴露 `subscriptionTitle` 与 `balance` → 前端三态视图。只增字段，旧前端忽略新字段即可，可以先上线观察首屏「未查询」的剩余比例。

**阶段二（P1 / P2，纯前端）**：标题 email + `#id`，徽章收敛。不动后端。

**阶段三（P3 / P5，breaking，必须一起发布）**：排序全序化 → 后端筛选 → 后端分页 → facets 端点 → 前端 `buildPageItems` → 筛选栏与分页组件 → 三处分页回归修复（实时余额存活范围、选中集合携带属性、全量清除语义对齐）→ 新增全选控件。排序修正与分页不能拆开发布，理由见 Decisions。三处回归修复也必须同批，它们是分页的直接后果，晚一个版本就是一个版本的错误计数。

**回滚**：阶段一、二回滚是纯代码回退，无数据迁移。阶段三回滚同样是代码回退，因为分页不改变任何持久化格式；但已经分享出去的带查询串的链接会在回滚后失效（参数被忽略，回到全量列表），这个降级是可接受的。

**验证**：`cargo check --release --all-targets` 零新增告警、`cargo test`、`cd admin-ui && pnpm test && pnpm build`、`openspec validate --all`。线上核实项见 docs 设计文档第 8.4 节。
